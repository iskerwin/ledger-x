# 04 云端测试与发布

## 日常操作

一项改动的路径：**分支 → PR 检查 →（需要时）预览包上手机 → 合并 → 开发版 → 手机验收 → 正式版**。main 只经 PR 合并，工具不直接推 main。

| 入口 | 怎么运行 | 做什么 | 约耗时 |
| --- | --- | --- | --- |
| **本机检查** | `python3 tools/ship.py check` | 与云端第一步相同的静态检查和工具测试；不编译 App | 1 分钟内 |
| **Ledger CI** | 提交 PR 后自动运行；每周日 22:00（北京时间）main 自动全量 | 与开发版同一套自动选测和执行程序；gate 通过才能合并；通过后留下 PR 测试记录，不发布。每周全量只验证 | 视改动 |
| **Ledger Preview** | 已推送的分支上 `python3 tools/ship.py preview`，或 Actions → Ledger Preview，Branch 选该分支 | 静态检查、工具测试、Release 编译，发布手机预览包（构建 N.k）；不能转正 | 约 10 分钟 |
| **Ledger Dev** | 最新 main 上 `python3 tools/ship.py dev`，或 Actions → Ledger Dev，Branch 选 **main** | main 与 PR 测过的文件树和选测一致时复用 PR 测试记录，只编译发布；否则自己跑相同的相关测试，通过后打包开发版 | 复用约 10 分钟 |
| **Ledger Release** | 手机验收后运行，Branch 选 **main**，只填 `accepted_build` | 对已验收包的同一源码补齐全量，通过后将原 IPA 转正 | 视全量 |

Dev 没有输入参数。版本、构建号、源码提交、校验值和任务编号由程序获取。Release 的 `accepted_build` 填安装并验收那一包发布说明中的「构建 N」，只填 N，例如 `123`；不能拿最新开发版编号代替已安装编号。App 设置 › 关于 Ledger X 显示版本和构建号（如「版本 1.0.8（构建 42）」），装的是预览包、开发版还是正式版可以从构建号分清。

CI（Continuous Integration，持续集成）检查、开发版可安装、手机验收、正式版发布是不同结果，分别记录。未验收写「待手机验收」。普通推送和 PR 不会自动发布。

## CI：合并前检查

每个面向 main 的 PR 都跑 `Ledger CI / gate`，不按路径跳过任务。它先实际加载共用发布组件，然后**用开发版的选测和执行程序**（`tools/dev_scope.py`）检查 PR 的合并结果：比较上次开发版到这次合并结果的全部改动，选测规则见下面 Dev 一节，静态检查和工具测试始终执行。阶段时限和单项 180 秒与 Dev 相同。选测范围是「上次开发版之后的全部改动」，所以连续合并很多 PR 而不发开发版时，后面的 PR 检查会越选越多，可能超过界面测试阶段时限；这时先在 main 上发一次开发版（通常复用最近 PR 的测试记录，只编译发布），之后的 PR 检查只比较新开发版之后的改动。

选测漏掉的问题由每周全量兜底：每周日 22:00（北京时间）`Ledger CI` 在 main 上自动跑一次完整全量（`schedule` 触发，与 `ship.py test` 相同），只验证，不发布安装包、不留 PR 测试记录。失败时照常上传日志和结果包，按真实原因开分支修复，不必等到转正前才发现。

PR gate 只读，不用编译缓存，不发布。同一 PR 新提交取消旧检查。任务总时限 90 分钟。通过后上传 PR 测试记录 `ledger-pr-proof-<运行号>`（保留 30 天），内容包括合并结果的文件树、选测基线、所选用例和通过数；失败时上传日志和结果包（保留 7 天）。

main 的保护规则（Settings → Branches → main）：必须经 PR、`gate` 检查通过、分支已同步最新 main（strict），管理员同样遵守，禁止强推和删除。因此合并后的 main 与 PR 测过的合并结果文件树相同，开发版可以直接复用这份记录。

## Preview：合并前上手机

```sh
git push origin fix/xxx          # 先推送分支
python3 tools/ship.py preview    # 在该分支上执行
```

- 只对已推送的分支当前提交；本地有未提交或未推送的改动时拒绝。
- 只做静态检查、工具测试和 Release 编译，打包内置同一份固定演示，校验后发布到 `preview` 预发布（只保留最新一个），并更新安装源。不跑模拟器测试，测试由 PR 检查负责。
- 构建号为「上次开发版号.序号」，例如开发版 41 之后依次是 41.1、41.2。它出现在**开发版安装源**里，排在开发版前面；合并后发布的开发版 42 更大，会直接覆盖安装。正式版安装源不列预览包。
- 发布说明写明分支、提交、PR 号和「不能转正」。Release 只接受当前开发版的构建号，预览包无法转正。
- 预览任务有自己的队列（`ledger-preview`），不阻塞开发版和正式版；同时更新安装源时，被拒绝的推送会重新生成后再推送，最多三次。

界面或交互改动，先发预览包，Kerwin 在手机上确认符合预期再合并；不符合就在同一个 PR 里继续改。

安装源只列最新一个预览包，新预览会顶掉旧的。所以新预览要包含之前预览过、还没合并的所有 PR：把它们合进一个预览分支（如 `preview/batch-N`），在上一个预览分支的基础上加新 PR，再对这个分支发预览包；发之前用 `git merge-base --is-ancestor <PR 提交> <预览分支>` 核对每个已预览未合并的 PR 都在里面。

### 外部贡献者的 PR

- 从 fork 提的 PR 同样自动跑 `gate`（只读，不需要密钥）。第一次提 PR 的人，要 Kerwin 在 PR 页面点「Approve and run」检查才开始。
- PR 落后于 main 时，在 PR 页面点「Update branch」同步，或贡献者自己合并最新 main 再推送；同步后 gate 重新运行。
- 预览包只能对本仓库里的分支做：需要上手机时，把 PR 的提交推成本仓库的一个分支（如 `git fetch origin pull/N/head:preview/pr-N && git push origin preview/pr-N`），对它发预览包；确认后仍合并原 PR，再删掉这个预览分支。
- 合并条件与本仓库分支相同：gate 通过、已同步最新 main、界面改动先预览确认。

### 合并后清理分支

仓库设置了合并后自动删除 PR 的分支（Settings → General → Automatically delete head branches）。没有自动删掉的，合并后手动删除远端和本机同名分支。预览分支（如 `preview/batch-N`）在其中的 PR 全部合并或关闭后删除；还开着的 PR、正在用的预览分支不删。没合并就关掉的 PR，分支由 Kerwin 决定。main 和 ipa 永不删除。删掉的 PR 分支可以在该 PR 页面点 Restore branch 恢复；开发版复用的 PR 测试记录存在 Actions 里，不受删除分支影响。

## Dev：少量、明确、可追踪

```sh
python3 tools/ship.py dev
```

只在干净、与 GitHub 一致的 main 上发起，客户端不推送。比较**上次开发版到本次 main 的全部净改动**，覆盖多个 PR、删除和重命名，不只看最后一个提交。基线来自开发版清单，并核对 dev 标签；读取失败、身份不符或网络错误时停止。

**复用 PR 测试记录**：选出测试范围后，Dev 查找最近 30 次通过的 PR 检查。若某次的文件树与本次 main 相同，且选测基线、核心筛选、界面用例和窄屏用例都与本次计划一致，就沿用它的通过记录，只做静态检查、工具测试和安装包编译；发布说明写明「由 PR 检查完成」并附链接。任何一项不同（例如合并时 main 已前进、期间发过开发版、记录过期）就照常运行下面的相关测试。

测试选择由 `tools/dev_scope.py` 决定：

- 有明确对应关系的功能，跑对应核心/存储测试和界面用例。例如月历覆盖明细、订阅与字号；演示加载只加演示仓库和加载隔离测试。
- 本次修改过的测试按 diff 选回归，不因测试类很大就自动跑整类；确实改到全类共用代码时仍按影响范围执行。
- App 代码变化另跑三个关键流程：已有交易无损编辑、快捷/完整表单共享金额、空表单关闭。
- 只改 `en.json` 或三个系统字符串目录（`Localizable`、`AppShortcuts`、`InfoPlist.xcstrings`）时，静态校验翻译与系统文案，开发版照常编译 IPA；以前附带的三个表单流程不再运行。其他资源仍保守处理；Swift 文件中的文案变化不按纯本地化文件处理。混合改动取各文件所需测试的并集。
- 共用组件文件（`ControlStyle.swift`、`Common.swift`、`Theme.swift`）按改到的组件选它的界面测试（`dev_scope.py` 的 `COMPONENT_UI`，例如改 `PeriodBar` 选月份栏用例、改 `ActionRow` 选操作按钮用例）。改到没有映射的组件时，摘要写明「完整覆盖留到转正前」，不拉起整套界面测试；新增共用组件且已有能看到它的界面测试时，同时补映射。
- 未映射的 App 页面或工程配置只加编译和关键流程，**不因此启动整套界面测试**。未知核心改动可扩大到核心模块；未知存储改动可扩大到 App 内模块。首次或非祖先基线按当前源码功能选测。
- 界面映射失效时停止并修正，不用整套界面测试兜底。App 内模块若需要扩大，必须有实际可执行的测试，不能把零项算通过。
- 只改文档和发布工具时做静态、工具检查；生成开发版仍需编译 Release IPA。

这是一轮开发回归，不代表跨功能完整覆盖。完整界面、独立 Beancount 报表对照和全部模块在转正前验证。Dev 不接受 `--full`，不生成可用于转正的全量证据。

执行前，日志和 Actions Summary 列出基线、改动文件、所选用例及原因，另保存 `.ship/dev-test-plan.json`。Dev 实时输出编译、当前用例和失败日志，各阶段有独立时限：

自动 Dev 与 PR 的计划不允许标为完整全量；扩大到核心或 App 内模块必须在 `reasons` 中说明，PR 日志也打印扩大原因。`check_project.py` 检查这两条路径的选测入口不得直接调用完整全量验证，并检查典型计划。手动 CI 留空范围仍按明确约定跑全量，不属于自动 PR 门禁。

| 阶段 | 上限 |
| --- | --- |
| 静态检查、工具测试 | 各 5 分钟 |
| 核心测试 | 12 分钟 |
| App 测试包编译 | 20 分钟 |
| 相关 App 内与界面测试 | 每轮 25 分钟，单项 180 秒 |
| Release IPA 编译 | 20 分钟 |

超时就失败，不发布；时限不是正常耗时承诺。所选测试都要实际通过，保留日志、结果包和截图。自动选测不再加跑窄屏：界面按可用空间和字号自适应，不按机型区分；窄屏只在手动 `--device` 指定时运行。

测试的 scheme 按目标选择：只选 `LedgerTests` 用 `LedgerHostedTests`，只选 `LedgerUITests` 用同名 scheme，同时选两层用 `LedgerInteractionTests`；全量用含两个 bundle 的 scheme。每个被选中的 bundle 仍编译其全部测试文件，SwiftPM 的 `--filter` 也只减少执行的用例。发布说明写明实际范围，Dev 记录为 `scope=build`。

相关测试通过后，流程依次检查开发中版本 → 计算构建号 → 编译 IPA 并内置固定演示 → 校验版本、签名资源、ZIP、演示内容与 SHA256 → 核对源码仍是最新 main → 发布开发版 → 更新安装源。任一步失败停止后续。

## Release：验收原包转正

1. 安装开发版，记下其构建号，按 [06 手机验收清单](06-手机验收清单.md) 验收。
2. 验收后执行，或明确授权执行：

```sh
python3 tools/ship.py release --accepted-build 123
```

程序绑定构建号与 IPA SHA256，核对包、源码、文件树和固定演示快照。当前开发版已被其他构建替换时拒绝转正。

全量记录必须绑定已验收包的同一源码、文件树和演示内容。已有有效记录就复用；缺少时在独立工作区检出**安装包对应提交**补跑，不能改测更新的 main。全量包括静态、工具、全部核心测试、Beancount 报表对照、全部 LedgerTests 和 LedgerUITests。两个 App 测试目标都必须有非零通过数；失败、跳过、漏跑、零项或结果不可读都不算通过。全量单项界面用例时限为 300 秒。

通过后发布**同一个 IPA**，不重新编译，不改版本号或构建号。没有手机验收不能转正；任何检查失败或中断都不发布。

## 单独验证

Ledger CI 也可手动运行：Branch 选待测分支，源码号和机型通常留空。`core_filter`、`ui_tests` 都留空是全量，填写后只跑指定测试。需要手填时，应给出可直接复制的测试值。

```sh
# 指定核心回归；不编译 App、不发布
python3 tools/ship.py test --core-filter 'CalendarMarkTests|PostingOrderTests'

# 指定 App 内/界面用例，可重复 --ui-test
python3 tools/ship.py test --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelection

# 窄屏；指定机型不可用时报错，不换成宽屏
python3 tools/ship.py test --device 'iPhone SE (3rd generation)' --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelection

# 完整验证，只测试、不发布
python3 tools/ship.py test --full
```

`--ui-test` 格式是 `Target/Class[/method]`。指定测试必须实际执行，核对通过数和每个选择器；不能用空结果冒充通过。`test` 针对当前已推送的分支（本机在哪个分支执行就测哪个），只验证；`dev` / `release` 只在与 GitHub 一致的 main 上发起。

## 查看进度、失败与重试

```sh
python3 tools/ship.py watch --once
python3 tools/ship.py watch
```

- `queued` 是等待执行机，`pending` 可能在等发布锁，不是测试失败。`in_progress` 也不代表已经通过。
- Dev 日志实时显示进度；原有手动验证与正式版全量流程保留各自日志。阶段状态在 `.ship/status.json`，客户端任务链接在 `.ship/cloud.json`。
- 失败后查看首个失败阶段、日志和 `.xcresult`。测试尚未开始的模拟器环境失败可重跑；业务失败要修原因，不删测试、不放宽断言、不反复重跑凑绿。
- 源码已合并但未产出包，写「源码已在 main，未发布安装包」。发布或安装源更新中途失败，要核实实际远端状态，不能一律写成没有发布。
- 修复代码后从 Run workflow **新建任务**；旧任务 Re-run 仍使用旧提交。
- 正在发布的任务不擅自取消；Dev 与 Release 共用发布锁，排队只保留最新任务。旧源码不能覆盖新开发版。取消或中断不算通过。

日志、截图、结果包及已产生的 IPA 副本保留 7 天，全量证据保留 30 天。超时或外部取消可能来不及上传全部证据。GitHub Release 上的 IPA 长期保留，不删除 Release、标签和 main、ipa 分支，不强推 main。

## 版本、安装源与环境

- 新版本在分支上用 `python3 tools/ship.py version patch|minor|major|X.Y.Z`，必须提高版本，在 CHANGELOG 顶部开始「开发中」一节，本地提交后经 PR 合并。每项改动累加更新记录；发布说明自动生成。
- Dev 构建号取 Release 说明与 ipa 分支安装源历史中的最大值加一；历史不完整或无法解析时停止。预览包为「当前最大号.序号」，不占用开发版编号。正式版沿用验收包的同一个号。
- 转正后，将 CHANGELOG 标题改成北京时间发布日期，单独提交；下一项改动开始新版本。
- 安装源位于 ipa 分支：`dev.json`、`release.json` 和对应 `mirror/` 文件。`dev.json` 列出开发版和最新预览包（按构建号从新到旧），再列正式版；`release.json` 只列正式版。安装工具使用用户自己的 Apple ID 签名，镜像由 gh-proxy.com 转发。
- 测试、模拟器、编译、打包和发布都在 GitHub 托管 `macos-26` 执行，Xcode 固定 26.6。Python 3.12、Beancount 3.2.0，已有 XcodeGen 不主动升级。本机只编辑、静态/工具检查、提交和发起云端任务。
- 只读取固定提交的公开演示库；测试和包内演示必须核对内容摘要，不读取私人账本。
- 缓存只用于依赖和测试编译产物；IPA 每次干净编译。缓存键以前只含工程配置，命中后不会更新；现在按源码摘要保存新缓存，只在系统、CPU 架构、Xcode 26.6、epoch、Package.swift、project.yml 和 Xcode 选择脚本相同的前缀下回退复用。配置、工具链或 epoch 变化即失效；源码变化仍执行编译命令，由编译器判断哪些产物可复用。测试每次实际运行，缓存不含结果包、验证证据或 IPA，不能凭命中认定通过。确认缓存损坏时才增大仓库 Actions Variable `LEDGER_CACHE_EPOCH`（默认 1）；日常不用填写，工作流解析后经输入传入共用组件。
- PR gate 只读；手动 CI 可保存缓存和证据；只有 Dev/Release 有发布权限。共用组件的内部 `check_only` 仅用于 PR 实际加载检查，不执行测试、打包或上传。

源码入口：工作流在 `.github/workflows/`（ci、preview、dev、release），共用步骤在 `.github/actions/ledger-run/`，本机派发为 `tools/cloud.py`，云端入口为 `tools/cloud_worker.py`，执行逻辑为 `tools/ship.py`。

## 本地目录保持精简

- 本机不编译 App、不跑 Swift 测试或模拟器。本机检查用 `python3 tools/ship.py check`；其他轻量 Python 检查使用 `PYTHONDONTWRITEBYTECODE=1`，日志和一次性检查副本放系统临时目录，结束后清理本次产生的文件。
- 旧的 `build/`、`build-demo/`、`LedgerKit/.build/`、`dist/`、`Payload/`、`*.xcresult`、`*.log`、生成的 `Ledger.xcodeproj/`、`samples/` 和 Python 字节码都属于可重建产物，任务结束及时清理，不留在项目里长期堆积。
- 删除前核对目录与 Git 跟踪状态。保留源码、冻结样本、文档素材、任务记录及用户未提交改动，不使用不分对象的 `git clean -fdx`。清理只影响本地生成物，不能删除远端 Release 和标签；远端分支只按下面「合并后清理分支」删除。
- 清理后核对项目大小和 Git 状态。仍被进程使用或未能删除的文件如实列出，不能写成已经清空。

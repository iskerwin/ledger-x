# 04 云端测试与发布

## 1. 一条流程

合并前的检查、开发版、手机验收、正式版是四步，不能互相代替。任何一步失败，都不发布安装包。

1. **合并前**：每个 Pull Request 自动跑「Ledger CI / gate」。它按改动做静态检查、工具测试和相关测试，权限只读，不发布。变绿才合并进 main。
2. **开发版**：合并之后，`python3 tools/ship.py dev` 比较上次开发版到当前 main 的全部净改动，自动选相关测试，无法缩小时扩大到受影响模块。Dev 不运行完整全量；这些测试通过，才编译并发布开发版安装包，无需手填参数。
3. **手机验收**：Kerwin 安装的就是这一版，按 [06](06-手机验收清单.md) 记下构建号。
4. **正式版**：`python3 tools/ship.py release --accepted-build N` 在这一版的同一源码上跑完全量测试（已有绑定到该提交和演示内容的全量记录时直接复用），通过后把**同一个安装包**转成正式版。不重新编译，不另编版本号或构建号。

分别汇报：源码提交、PR 检查、指定或全量测试的实际结果、安装包和发布状态、手机验收。编译成功不能代替测试通过，相关测试不能代替全量，未验收一律写「待手机验收」。

测试、模拟器、Release 编译、打包、开发版发布、正式版转正和 IPA 源更新在 GitHub Actions 的 macOS runner 上执行。本机只编辑、做轻量静态/工具检查、提交、开 PR、合并后普通推送并发起云端任务，不启动 Xcode 编译或模拟器。

CI 是 Continuous Integration（持续集成），这里指合并代码前的自动检查。Actions 分成三个独立入口：

| Actions 名称 | 文件 | 触发与结果 |
| --- | --- | --- |
| Ledger CI | `.github/workflows/ci.yml` | PR 自动按改动检查；也可手动指定测试或跑全量。只验证，不发布 |
| Ledger Dev | `.github/workflows/dev.yml` | 手动发开发版；无输入参数，自动选相关/模块测试，通过后打包，待手机验收 |
| Ledger Release | `.github/workflows/release.yml` | 手机验收后手动转正；核对验收包并补齐同一源码的全量，原 IPA 不重新编译 |

命令行入口仍是 `python3 tools/ship.py`：本机调用时转交 `tools/cloud.py`，按 `test`、`dev`、`release` 分别触发对应工作流。runner 共用 `.github/actions/ledger-run/action.yml` 和 `tools/cloud_worker.py`，测试与打包逻辑不复制三份。普通推送和 PR 不会发布。开发版和正式版只能对着已经在 main 上的源码。云端失败时，源码可能已经在 main，结论写「源码已在 main，未发布安装包。」本机命令还没把任务发出去就失败时，仍写「未发起推送或发布。」

### 网页操作与输入

打开仓库 **Actions → 对应工作流 → Run workflow**。Dev、Release 的 **Branch 必须选 main**；手动 CI 可以选待验证的分支，PR 自动 CI 不需要操作。

| 入口与字段 | 填什么 |
| --- | --- |
| CI：`core_filter`、`ui_tests` | 两项都留空是全量；只查相关测试时按下面的格式填一项或两项。手动 CI 的全量与 PR 自动按改动检查是不同范围 |
| Dev：无输入参数 | **Branch 选 main，直接 Run workflow**。自动选相关/模块测试；源码固定为触发时的 main，不运行完整全量 |
| CI：`core_filter` | 核心测试类名，例如 `CalendarMarkTests`；多类用 `CalendarMarkTests\|PostingOrderTests`，填写时不加反引号或引号 |
| CI：`ui_tests` | `Target/Class` 或 `Target/Class/method`，例如 `LedgerTests/AppearanceTests`；多个用空格分隔。手动复查时由开发助手给出可直接复制的具体值 |
| CI：`device` | 通常留空自动选机型；窄屏检查填 `iPhone SE (3rd generation)`。指定机型不可用时失败，不换成宽屏 |
| CI：`source_sha` | 网页无需填写，自动使用所选分支在触发时的提交；命令行自动填写以锁定本地提交 |
| Release：`accepted_build` | 只填你安装并验收那一包发布说明里的「构建 N」的 N，例如 `123`。安装时记下构建号；不能把最新开发版编号当成已安装编号。App「关于」目前只显示版本号，不显示构建号 |

版本号、下一构建号、请求/任务编号、IPA SHA256 和演示快照均由程序读取或计算，不需要手填。Release 只保留 `accepted_build` 一个输入，当前开发版已被其他构建替换时拒绝转正。

## 2. PR 门禁

工作流是 `.github/workflows/ci.yml`，名称 **Ledger CI**，PR 任务名保留 **gate**。对着 main 的每个 Pull Request 都会跑，没有路径过滤：被跳过的必需检查会卡住合并，所以这里总是跑同一个任务。

它做三件事，然后结束：

- `tools/check_project.py` 和 `python3 -m unittest discover -s tools/tests -p 'test_*.py'`。
- 按 `tools/pr_scope.py` 看 diff：只改文档或工具时不编译。改了 LedgerKit 源码就跑全部 `swift test`；只改个别 LedgerKit 测试文件就跑这些类。改了 `project.yml`、`Ledger/`、`LedgerTests/` 或 `LedgerUITests/` 就编译 App 测试包。改了测试文件时，只跑 diff 碰到的用例（`Target/Class/method`），不跑整个类，也不跑整套界面测试。这些用例如果都是月历（方法名里带 Calendar），就一并跑上同一文件里其余月历用例。大家共用的辅助函数（例如启动、点按）有改动时，才把调用它的用例都算上。改动落在类外面（例如 import）时仍跑整个类。
- 任务限时 60 分钟。核心测试、编译、界面测试各自还有更短的进程时限，到点就停。每条界面用例最多 180 秒（`xcodebuild -test-timeouts-enabled YES -maximum-test-execution-time-allowance 180`）。模拟器开机和等到就绪各最多 120 秒。PR 检查不用编译缓存，所以编译会比命中缓存的发布任务慢，但不会一直挂着。
- 打印「PR 门禁通过；未发布安装包」。

PR gate 权限只有 `contents: read`。不使用编译缓存，不上传产物，不能推送，不能创建 Release。同一个 PR 新推送会取消还在跑的旧检查，只留最新一次。手动 CI 使用单独的 `test` 任务，可保存测试缓存和验证证据，同样不能推送或发布。

PR gate 在常规检查前实际加载共用 `ledger-run` 组件，以内部 `check_only=true` 跳过所有环境准备、测试、缓存、截图和上传步骤，仅确认组件能加载。它不改变相关测试的选择范围，也不发布。缓存代次在 CI、Dev、Release 工作流中读取仓库变量，再经组件的 `cache_epoch` 输入传入；组件不直接读取工作流专用的 `vars` / `secrets` 上下文。

**合并进 main 需要这次检查是绿的。** GitHub 上显示的工作流与任务是 `Ledger CI / gate`。实际保护规则里的检查上下文以 PR Checks 列表为准，可能只显示 `gate`。从旧名 Ledger PR 迁移时，任务名 gate 保持不变；如果旧规则绑定了工作流显示名或文件路径，管理员需同步核对并更新，不能通过跳过门禁解决。这里不自动修改仓库保护规则。

把它设成 main 的必需状态检查（Kerwin 用有管理员权限的账号操作一次即可）：

1. 打开仓库 **Settings → Rules → Rulesets**（或 **Settings → Branches** 里 main 的分支保护）。
2. 目标分支选 `main`。
3. 勾选必须通过 Pull Request 才能合并。
4. 勾选必须通过状态检查，在列表里选中 `Ledger CI / gate`（或 Checks 里实际显示的 `gate`）。
5. 保存。

设好之前，有管理权限的人仍可以直接合并。检查本身从工作流进入 main 之后就会在每个 PR 上显示通过或失败。PR 变绿只说明这次 diff 的相关检查过了，不发布安装包，也不代替下面的开发版和正式版。

## 3. 一次性配置

- 仓库启用 Actions。测试和发布用 GitHub 托管 `macos-26`，不使用本机 runner。
- 本机安装 Python 3 和 `gh`，执行 `gh auth login`。登录需能推送仓库、修改 workflow、触发和查看 Actions。
- 手动测试任务的权限是 `contents: read` 加上保存产物和缓存使用的 `actions: write`，不能推送或发 Release。只有发布任务才有 `contents: write`。PR gate 没有写权限。不需要上传个人 Token 或 Apple 签名证书。
- 在 main 以外触发 dev 或 release 时，一个很短的 Ubuntu 任务直接失败，避免「没有任务却显示成功」。
- `tools/select_xcode.sh` 固定 `/Applications/Xcode_26.6.app`。找不到，或 `xcodebuild -version` 不是 26.6，就失败，不改用镜像里的其他 Xcode。`ship.py` 在云端再核对一次。另外安装 XcodeGen（已有则不升级）、Python 3.12 和固定的 Beancount 3.2.0。IPA 仍是临时签名，用户在手机安装工具里用自己的 Apple ID 签名。
- 测试和安装包只能克隆公开演示库 `https://github.com/iskerwin/ledger-demo`，并固定到 manifest 里的提交。地址不是这个库就拒绝。永不读取私人账本。
- 手动测试和发布任务缓存 Swift 包和测试编译产物（`LedgerKit/.build`、`build-demo` 里的包和编译结果）。缓存键带 Xcode 26.6、仓库变量 `LEDGER_CACHE_EPOCH`（未设置时为 `1`）和工程文件哈希。不缓存 `build/`：开发版 IPA 每次干净编译。转正补跑全量时用独立工作区，不用这份缓存。缓存只在任务成功后保存。只有确认缓存损坏时，才在 Settings → Secrets and variables → Actions → Variables 增大 `LEDGER_CACHE_EPOCH`；日常不填写缓存参数。PR 检查不用缓存。
- 开发版和正式版跨工作流共用 `ledger-publication` 并发组，`cancel-in-progress: false`。正在发布的任务不会被取消。后面又排进来的发布会取消更早还在排队的发布，所以排队里只留下最新一次。手动测试任务按 GitHub 运行编号分开，可以并行。
- 体积大的日志、`.xcresult`、截图和安装包副本保留 7 天。很小的全量证据 `.ship/full-validation.json` 保留 30 天。GitHub Release 上的安装包长期保留。证据过期后，转正会在同一源码上重跑全量。

## 4. 日常开发与指定回归

先提交，维护 CHANGELOG，开 Pull Request。门禁绿了再合并。合并后如果要发开发版或单独复查，再发起云端任务。命令会检查工作区干净、当前在 main、没有落后远端，然后普通推送并发送任务。返回任务链接不代表测试通过。

非 main 分支可以只跑测试：在 Actions 里手动触发 Ledger CI，Branch 选该分支，`source_sha` 留空即可自动取该分支当前提交。两个测试筛选都留空就是全量。这种任务只读，不发布。`ship.py` 在本机发起时仍先推送 main，因为开发版和正式版只能在 main 上发布。

```sh
# 只跑指定核心测试，不编译 App，不发布
python3 tools/ship.py test --core-filter 'CalendarMarkTests|PostingOrderTests'

# 只跑一个必须看界面的回归；自动编译 App 和测试包
python3 tools/ship.py test --ui-test LedgerUITests/EditInteractionTests/testCalendarUsesFullRowWidthWithoutHint

# 同一任务可组合核心和多项界面/App 内回归
python3 tools/ship.py test --core-filter CalendarMarkTests \
  --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelection \
  --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelectionAtLargeText

# 指定窄屏机型；运行时不支持就报环境问题，不偷偷换宽屏
python3 tools/ship.py test --device 'iPhone SE (3rd generation)' \
  --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelection
```

`--ui-test` 支持 `Target/Class` 或 `Target/Class/method`，可重复。`--core-filter` 沿用 `swift test --filter` 语法。指定测试必须实际执行、有通过数、没有失败或跳过，并核对请求的每个选择器都执行到了。空结果不能算通过。指定回归记录为 `scope=build`，包含实际筛选、通过数和设备，永不写成全量记录。

测试分层：LedgerKit 放解析、金额、格式、报表逻辑；LedgerTests 放必须在 App 内运行的存储、上传、恢复；LedgerUITests 放键盘、弹层、手势、跳转、布局。每个 bug 配修复前会失败的最低层回归。涉及共用组件、保存、同步、隔离或记账计算时扩大相关模块范围。切换布局检查常用字号、较大字号与窄屏。

本机只做轻量检查：

```sh
python3 tools/check_project.py
python3 -m unittest discover -s tools/tests -p 'test_*.py'
git diff --check
```

只改文档或工具时不用编译未变动的 App。调试和测试编译会提示类型检查超过 200 毫秒的表达式；Release 安装包不带这个提示。

## 5. 验证后打包并发布开发版

```sh
# 日常：自动选择上次开发版之后所有改动的相关测试，通过才打包发布
python3 tools/ship.py dev

```

网页打开 Ledger Dev，Branch 选 main，直接 Run workflow。Dev 没有输入参数，不接受 `--full`、手填测试或机型；需要单独复查时用 Ledger CI 或 `ship.py test --core-filter … / --ui-test … / --device …`，只验证、不发布。完整全量在手机验收后、Release 转正前对同一源码执行；也可提前用 `test --full` 只做验证。

自动选测由 `tools/dev_scope.py` 负责，不改变 PR CI 的选测规则：

- 从当前 dev Release 的 build-manifest.json 读取上次开发版源码，并与 dev 标签核对。用该提交到本次源码的直接 diff，覆盖多个 PR 累积的新增、修改、删除和重命名，不只看最后一个提交。
- 已建立明确对应规则的源码运行对应测试，并合并改动测试文件涉及的回归。当前月历规则覆盖 CalendarMarkTests、SearchTests、SubTests，以及明细、订阅、系统月历回退、字号/布局相关的 9 项界面回归；另在 iPhone SE 第三代跑明细和订阅的常用/较大字号 4 项回归。同步状态显示源码对应 SyncAppearanceTests。
- 文档、发布工具和工作流改动执行静态与工具测试，不因此跑未改动的 App 回归；开发版仍需编译 Release IPA。演示快照/报表样本改动扩大到核心与 App 内模块。
- 没有精确对应规则时按层扩大：LedgerKit 源码跑核心模块；存储/同步源码跑核心和 App 内模块，Store、Shared、Compose、Backends 这类共用状态另含界面模块；其余 App 源码、资源或工程改动跑 App 内和界面模块。无法判断的文件覆盖各模块；这可能仍耗时较长，但不会触发包含独立 Beancount 报表对照的完整全量流程。
- 首次开发版或基线不是当前源码的祖先时，按当前全部受版本管理源码所含模块选测。测试已删除或对应规则过期时，改跑当前受影响模块，不继续使用已失效选择器；模块没有测试时停止。基线清单读不出、身份不匹配或网络请求失败时停止，不能把它伪装成“没有改动”。
- 扩展局部选测时，在 MAPPINGS 中补实际依赖与测试，并更新工具回归。不能仅按测试名包含文件名来猜。

任务日志和 Actions Summary 在执行测试前列出比较基线、全部改动文件、所选测试和扩大模块范围的原因，并保存 `.ship/dev-test-plan.json`。核心模块用 `.*` 选择全部核心测试，App 模块枚举当前存在的测试类，必须实际执行；各模块都运行过仍记为 `scope=build`，不生成可用于转正的全量证据。发布说明记录实际范围和各机型通过数。普通与窄屏测试都必须通过，两个结果包和截图都保留。

顺序：确定并展示相关/模块测试范围 → 静态检查与工具回归 → 相关/模块回归 → 核对版本仍在开发中、正式标签尚未占用这个版本号 → 计算构建号 → Release 编译并内置固定演示 → 校验签名资源、版本、ZIP、演示内容和 SHA256 → 核对源码没变化且仍是远端 main 最新提交 → 发布开发版 → 更新 IPA 源。任何前置步骤失败都停止后续。旧源码任务不会覆盖较新的开发版。已运行的旧 Dev 任务仍按其绑定的源码和旧规则执行，不取消、不改写其测试范围。

发布说明必须写明实际验证范围。已知测试失败要报告 Kerwin，由他决定下一步。网络错误可能留下已更新的 Release 或部分附件；先查实际状态再重试。不删除 Release、标签或分支，不强推 main。

## 6. 完整测试

```sh
python3 tools/ship.py test
# 或明确写 --full，效果相同
python3 tools/ship.py test --full
```

只验证，不打包或发布，不能和指定筛选混用。云端串行执行：静态与工具回归 → LedgerKit 全部测试 → Beancount 报表对照 → 新建专用模拟器、关闭硬件键盘并确认启动 → 编译 App 和测试包 → 全部 LedgerTests 与 LedgerUITests。

以 `Reports match Beancount` 为报表一致结论。样本加载的预期提示不是失败。界面测试不并行，每项时限 300 秒。读取 `.xcresult` 汇总和用例明细，两个测试目标都要有非零通过数。失败、跳过、零项、漏目标或结果不可读均不算全量通过。验证记录绑定源码 SHA、文件树、演示提交与内容摘要，并记录运行链接、Xcode、设备、核心与两个 App 测试目标的通过数。

失败即停。未运行、失败、中断分别记录。不删测试、不放宽断言、不靠重跑凑绿、不用固定延时掩盖时序。测试尚未开始的模拟器环境失败可重跑。

## 7. 手机验收与正式版

Kerwin 安装开发版，按 [06](06-手机验收清单.md) 验收，明确记下构建号。只有验收后由 Kerwin 执行，或明确授权代为执行：

```sh
python3 tools/ship.py release --accepted-build N
```

`N` 是安装并验收那一包的构建号，安装时从该包的发布说明「构建 N」记下。本机先读取当前开发版清单核对构建号；云端在准备步骤再次核对，并自动将 IPA SHA256 绑定到后续步骤。之后重新下载开发版，核对绑定的 SHA256、大小、版本、构建号、签名资源、演示内容、源码在 main 上、标签与源码一致。验收身份对不上就停止。网页手动发起 Ledger Release 只填 `accepted_build`，SHA256 由同一准备步骤自动获取，不能用最新构建号代替实际验收的构建号。

正式版使用这份安装包上的版本号和构建号，不调用构建号递增。全量证据必须绑定这个安装包的源码 SHA、文件树和演示内容。证据还在（30 天内的全量 artifact，或开发版自己带的完整记录）就复用。缺少时，在独立工作区检出**安装包对应的那次提交**补跑全量，不能改测最新的 main。全量失败或中断就停止，不发布。

通过后把原 IPA 原样发布为正式版，不重新编译，并更新正式版源。正式标签和 Release 一经发布不覆盖、不移动、不删除。发布后单独把 CHANGELOG 的「开发中」标题改为北京时间的发布日期，提交并普通推送。下一版本仍用 `ship.py version` 开始。转正不会自动触发，这次开发任务通过也不等于已经授权转正。

## 8. 版本号和构建号

版本号（`MARKETING_VERSION`，安装包里的 `CFBundleShortVersionString`）是 `X.Y.Z`，不含前缀和前导零。只有下面这条命令能提高它，而且必须高于当前版本。命令在本机修改 `project.yml` 和 CHANGELOG 并提交，不编译、不发布：

```sh
python3 tools/ship.py version patch|minor|major|X.Y.Z
```

同一次版本开发期间，开发版继续用这个版本号，CHANGELOG 往「（开发中）」这一节里加。发开发版时，CHANGELOG 第一个 `## ` 标题必须是 `## 当前版本（开发中）`。如果 `v当前版本` 已经存在，说明这个号发过正式版，要先执行 `ship.py version` 开下一个号。

构建号（`CFBundleVersion`）是不含前导零的正整数。开发版和正式版共用一串号。发开发版时取两类数字的最大值再加一：GitHub Release 说明里的「构建 N」，以及 `ipa` 分支历史上 `dev.json`、`release.json` 里出现过的 `buildVersion`。发布列表不完整就停止。已经有发布或安装源，却一个构建号都读不到时，拒绝从 1 重新编号。全新空仓库的第一次构建号才是 1。

正式版不重新取号。版本号和构建号都等于手机验收过的那个开发版安装包。

当前仓库上的版本和构建号不写进手册，以 [Releases](https://github.com/iskerwin/ledger-x/releases) 和安装源为准。发布说明由 CHANGELOG 生成，并写明这次是相关测试、全量，以及手机验收状态。

## 9. 任务、日志和截图

```sh
python3 tools/ship.py watch --once
python3 tools/ship.py watch
# 也可直接用任务链接，或 gh run view / gh run watch / gh run download
```

客户端在 `.ship/cloud.json` 保存源码、工作流和任务编号，不会在本机跑测试。GitHub 派发接口直接返回任务编号和链接，无需手填请求编号。客户端被关闭时云端继续执行。每轮都有独立任务链接；`watch` 仍兼容旧 Ledger cloud 的已有记录。错误或中断时核查 main、Actions、Release 与安装源，不一律声称「未推送、未发布」。

手动 CI、Dev、Release 无论成功或失败，都上传 7 天的日志和产物：阶段状态、核心/工具/编译/交互日志、`.xcresult`、导出截图、实际验证记录，以及已经产生的 IPA、清单和说明。全量证据另留 30 天，转正可复用拆分前 Ledger cloud 留下的有效证据。PR gate 不上传产物。日志里可能有失败前的部分结果。只有任务结论和完整证据一致才算通过。runner 超时或外部取消时可能来不及收集全部附件，不能写成通过。

## 10. 安装源

IPA 源在 `ipa` 分支：`dev.json`、`release.json`、`mirror/dev.json`、`mirror/release.json`。地址和自签安装方式不变，镜像仍由第三方 gh-proxy.com 提供。安装工具用用户自己的 Apple ID 重新签名。

## 11. 云端环境依据

runner 标签与预装软件以 GitHub 官方 [runner 说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job) 和 [macOS 26 镜像清单](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md) 为准。Xcode 固定为 26.6，不随镜像里的其他 Xcode 漂移。模拟器运行时仍记录到每次任务里，不把某轮设备结果说成所有系统版本都已验收。

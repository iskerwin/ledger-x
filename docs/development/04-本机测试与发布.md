# 04 本机测试与发布

开发、测试、编译和发布均在 Kerwin 的 Mac 上完成。工作顺序是：修改 → 相关测试 → 构建与本地检查 → 开发版 → 手机验收 → 正式版。

日常按改动范围测试，准备正式版时做全量回归。构建成功、自动化测试通过、手机验收通过分别记录。

## 1. 准备环境

| 工具 | 用途 |
| --- | --- |
| Xcode 与 iOS 模拟器运行时 | 编译 App、运行模拟器与测试；运行时在 Xcode → Settings → Components 安装 |
| XcodeGen | 从 project.yml 生成 Ledger.xcodeproj，安装：`brew install xcodegen` |
| Beancount | 核对账务计算与报表，安装：`brew install beancount` |
| gh | 上传发布包与更新安装源，先执行 `gh auth login` |

命令行可设置 `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`，或执行 `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`。发布脚本会自动尝试使用该位置的完整 Xcode。

仓库放在普通本地目录。iCloud Drive 等同步目录可能给构建产物加扩展属性，影响代码签名。

测试只用虚构样本。`.demo-data` 是发布脚本准备的只读演示快照，固定提交见 tools/fixtures/manifest.json；测试和安装包使用同一快照。不读取或修改私人账本。

## 2. 日常开发：先选测试范围

每项改动运行能覆盖它的最低层测试；修 bug 补一个修复前会失败的回归用例。

| 改动内容 | 验证范围 |
| --- | --- |
| 文档、开发约定 | 静态检查 |
| Python 工具、打包与发布流程 | 对应工具测试与静态检查 |
| 解析、金额、汇率、交易生成、业务规则 | LedgerKit 中相关类或用例；涉及金额与报表时加 Beancount 对照 |
| 保存、上传、恢复、本机存储 | LedgerKit 相关逻辑与 LedgerTests 中对应模块 |
| 页面、键盘、弹层、手势、跳转 | 对应 LedgerUITests；在 Xcode 模拟器或真机检查实际操作 |
| 共用组件、同步、数据隔离、多模块改动 | 覆盖所有受影响的调用处，扩大到相关模块；影响面不明确时做全量回归 |

修改 App 后确认能构建。只改文档或工具时，完成对应检查即可。

同页切换内容时，检查切换前后的高度和位置；常用字号、较大字号与窄屏各看一次，并用相关界面回归测试覆盖。

### 命令行验证

```sh
# 静态检查
python3 tools/check_project.py

# 工具回归，可用具体模块或用例进一步缩小范围
python3 -m unittest discover -s tools/tests -p 'test_*.py'

# 只运行相关核心测试
LEDGER_DEMO_PATH="$PWD/.demo-data" SAMPLE_OUT="$PWD/samples" \
  swift test --package-path LedgerKit --filter PostingOrderTests

# 增删文件或修改 project.yml 后生成工程
xcodegen generate

# 仅构建 App
xcodebuild build -project Ledger.xcodeproj -scheme Ledger \
  -destination 'generic/platform=iOS Simulator' -derivedDataPath build-demo CODE_SIGNING_ALLOWED=NO

# 编译当前源码并运行一个界面用例
xcodebuild test -project Ledger.xcodeproj -scheme LedgerInteractionTests \
  -destination 'platform=iOS Simulator,name=Ledger Local Tests' -derivedDataPath build-demo \
  -parallel-testing-enabled NO \
  -only-testing:LedgerUITests/EditInteractionTests/testTagPickerCancelDoesNotChangeDraft \
  CODE_SIGNING_ALLOWED=NO
```

模拟器名称使用本机已有的设备；也可在 Xcode 中创建。`-only-testing` 可以指定测试类或用例，多项可重复该参数。修改源码后使用 `xcodebuild test` 重新编译；`test-without-building` 只用于当前源码已经完成测试包编译的情况。

### 在 Xcode 中验证

1. 运行 `xcodegen generate`，打开 Ledger.xcodeproj。
2. 选择 `Ledger` scheme 和模拟器，Build 检查编译，Run 检查相关页面和操作。
3. 自动化测试选择 `LedgerInteractionTests` scheme，在 Test navigator 运行对应的类或用例。
4. 汇报具体设备、测试范围和结果。手工操作记为手工检查，不能写成自动化测试通过。

## 3. 提交与失败处理

一件事一个提交，直接在 main 上提交。提交前完成本次改动的相关验证，并记录哪些通过、哪些未跑、哪些失败或中断。

测试失败先查业务、测试代码和环境的实际原因，不删测试、不放宽断言、不改门槛、不靠反复重跑凑绿，不用固定延时掩盖时序。测试尚未开始的模拟器环境失败可以直接重跑。

已知失败先向 Kerwin 报告，由他决定开发版是否继续；未执行的项目不能代替失败记录。发布脚本自身的检查、编译或打包失败时，停止推送和发布。

## 4. 发布开发版

相关测试与本地检查完成、改动已提交后执行：

```sh
python3 tools/ship.py dev
```

脚本按顺序完成：

1. 检查当前是 main、工作区干净、本地包含远端 main。
2. 执行静态检查和工具回归。
3. 准备固定演示快照，确定版本与递增构建号。
4. 编译 iOS 设备 Release 安装包，加入内置演示并签名；校验版本、构建号、签名、ZIP 与演示资源。
5. 确认源码在检查与编译期间没有变化，生成 IPA、源码清单和实际验证记录。
6. 普通推送 main，上传开发版，更新 IPA 安装源。

默认开发版发布记录为 `scope=build`：静态检查、工具回归、Release 构建与安装包校验。开发中独立运行的相关测试或 Xcode 手工检查单独汇报，不自动计入这份记录。

需要在发布开发版时执行全量回归：

```sh
python3 tools/ship.py dev --full
```

全量通过后再编译和发布，记录为 `scope=full`。发布说明依据记录写明实际验证范围。

Kerwin 安装开发版后，按 [06 手机验收清单](06-手机验收清单.md) 检查本次改动及受影响功能。发现问题先报告，由 Kerwin 决定修复或撤回；没有验收结论时写“待手机验收”。

## 5. 全量回归

准备正式版、影响范围较大或需要整体排查时执行：

```sh
python3 tools/ship.py test
```

该命令只验证，不发布。依次运行：

1. 静态检查与工具回归。
2. LedgerKit 全部核心测试，并生成 samples/reports.json。
3. 用 Beancount 对照报表，以 `Reports match Beancount` 为通过结论；样本加载提示中的 `N errors loading the sample` 属预期输出。
4. 新建专用模拟器 `Ledger Local Tests`，关闭硬件键盘，等待启动与系统服务就绪。
5. 生成工程，编译 App、LedgerTests 和 LedgerUITests。
6. 串行运行全部 App 内与界面测试，单项时限 300 秒。

完整结束且全部通过才算全量验证通过。中断只保留已完成项目的结果。

界面测试每次从独立虚构账本状态启动，隔离旧队列、文件树、历史与路径设置。验证实际保存和同步时使用独立文件夹副本。

## 6. 转正式版

Kerwin 手机验收通过后执行，或明确授权代为执行：

```sh
python3 tools/ship.py release
```

脚本下载当前开发版，核对安装包 SHA256、大小、版本、构建号、签名资源、演示资源、验证记录以及远端 main 中的源码提交和文件树。

- 安装包已有完整全量验证记录时，复用该记录；本机 `test` 留下的同一源码与演示快照的全量通过记录也可复用。
- 只有构建检查记录时，对安装包的同一源码、同一演示快照补跑全量回归。工作区必须干净，HEAD 必须等于安装包源码提交。已经继续开发时，在独立工作区检出该提交后执行 `release`。
- 全量失败或中断时停止。通过后将完整记录写入正式版发布附件，再发布正式版并更新安装源。

正式版使用手机验收过的同一个 IPA，不重新编译 IPA。在干净工作区运行 `test` 全部通过后，结果保存在 `.ship/full-validation.json`，绑定源码提交、文件树和演示快照，`release` 匹配后直接复用。工作区有未提交改动、测试失败或中断时，不生成可复用记录。`release` 补跑全量通过后也保存记录，后续上传失败重试无需重复测试；已发布开发版的附件由正式版发布时补齐。

版本号、CHANGELOG 与发布后的收尾规则见 [AGENTS.md](../../AGENTS.md) 的“发布”。

## 7. 版本号、构建号与更新记录

| 项目 | 自动维护方式 |
| --- | --- |
| 版本号 X.Y.Z | 开始下一版本时用 `version patch`、`minor`、`major` 或具体版本号；脚本计算并写入 project.yml，创建 CHANGELOG 小节并提交 |
| 构建号 | 每次发布开发版，从发布列表与安装源历史中的最高构建号加 1；同一版本可以有多个开发构建 |
| CHANGELOG | 开发助手在每项功能或修复的同一个提交中补齐用户可见变化，保留当前版本累计条目，Kerwin 无需手写 |
| 开发版发布说明 | 从当前 CHANGELOG 与上一次开发版做差异，自动生成本次变化、验证范围、构建号和安装包 SHA256 |
| 正式版发布说明 | 从安装包对应源码的 CHANGELOG 自动生成该版本完整记录 |

```sh
python3 tools/ship.py version patch        # 例如 1.0.7 → 1.0.8
python3 tools/ship.py version minor        # 例如 1.0.7 → 1.1.0
python3 tools/ship.py version major        # 例如 1.0.7 → 2.0.0
python3 tools/ship.py version 2.1.0        # 指定目标版本
```

当前版本仍在开发中时，继续累积本版本的改动，不因每次修改或每次开发版发布而升级版本号。正式发布后，开发助手把 CHANGELOG 标题改为北京时间的发布日期，单独提交并普通推送 main；开始下一版本时再运行 `version`。

## 8. 进度与产物

```sh
python3 tools/ship.py watch          # 持续显示进度
python3 tools/ship.py watch --once   # 查看一次
```

进度来自 `.ship/status.json`，包括当前阶段、用时、通过数、失败用例与最终结果。进程退出但未留下结论时显示中断。watch 只读，不影响正在运行的命令；`.ship/history.json` 保存上次通过的项目总数。

| 位置 | 内容 |
| --- | --- |
| tools-tests.log | 工具回归日志 |
| swift-tests.log | 核心测试日志 |
| reports-check.log | Beancount 对照日志 |
| demo-build.log | 模拟器测试包编译日志 |
| interaction-tests.log、interaction-tests.xcresult | App 内与界面测试日志、截图和诊断 |
| build.log | iOS 设备 Release 编译日志 |
| dist/Ledger.ipa | 开发版安装包 |
| dist/validation-evidence.json | 实际验证范围与结果 |
| dist/build-manifest.json | 源码、文件树、版本、构建号与安装包 SHA256 |
| dist/release-notes.md | 发布说明 |

上述日志与产物不入库。测试、构建与发布命令在本机串行执行，避免互相覆盖模拟器、日志和产物。

## 9. 安装源与发布边界

`ipa` 分支保存开发版与正式版安装源，各有 GitHub 直连和镜像地址：

| 渠道 | GitHub | 镜像 |
| --- | --- | --- |
| 开发版 | `https://raw.githubusercontent.com/<仓库>/ipa/dev.json` | `https://gh-proxy.com/https://raw.githubusercontent.com/<仓库>/ipa/mirror/dev.json` |
| 正式版 | `https://raw.githubusercontent.com/<仓库>/ipa/release.json` | `https://gh-proxy.com/https://raw.githubusercontent.com/<仓库>/ipa/mirror/release.json` |

在 SideStore、AltStore 或 Zeus 等支持 IPA 源的工具中添加地址，用自己的 Apple ID 重新签名安装。镜像由第三方 gh-proxy.com 提供，不可用时改用直连。

发布列表读取不完整时，脚本重读并用远端标签核对，仍缺失则停止。构建号取所有发布记录与安装源历史中的最大值加 1。生成安装源时也检查已有发布是否齐全，避免覆盖为空源。

正式版不覆盖、不移动标签；不删除 Release、标签或分支，不强推 main。更新安装源只清理临时工作目录；首次创建使用独立分支名，失败后可重试。

# 04 本机测试与发布

测试、编译和发布都在 Kerwin 的 Mac 上执行，唯一入口是 `tools/ship.py`。任何一步失败都停下：不推送、不发布。本机测试通过、可以安装、手机验收是不同的事实，分别说明。

## 环境

| 需要 | 说明 |
| --- | --- |
| Xcode 与 iOS 模拟器运行时 | 最好 `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`；未切换时脚本自动使用 `/Applications/Xcode.app` |
| XcodeGen、Beancount | `brew install xcodegen beancount`；Beancount 用 Homebrew 自带的 Python 运行 |
| gh | `gh auth login`，发布时上传 Release 与更新 IPA 源 |
| 演示快照 | 首次运行自动把 `ledger-demo` 克隆到 `.demo-data`，固定在 `tools/fixtures/manifest.json` 的 `demoCommit`，只读 |

仓库不要放在 iCloud Drive 等同步目录：同步服务给构建产物加的扩展属性会让代码签名失败。

## 命令

```sh
python3 tools/ship.py test                         # 全部验证，不发布
python3 tools/ship.py dev                          # 验证 → 编译 IPA → 推送 main → 更新开发版与 IPA 源
python3 tools/ship.py release                      # 手机验收后，把当前开发版原样发布为正式版 vX.Y.Z
python3 tools/ship.py version patch|minor|major|X.Y.Z   # 提交新版本号与 CHANGELOG 小节
```

只想快速检查时可以单独运行：

```sh
python3 tools/check_project.py
python3 -m unittest discover -s tools/tests -p 'test_*.py'
LEDGER_DEMO_PATH="$PWD/.demo-data" SAMPLE_OUT="$PWD/samples" swift test --package-path LedgerKit --filter PostingOrderTests
```

## test：验证步骤

1. 静态检查：文档链接、图片清单、冻结样本哈希、工程配置；`tools/tests` 工具回归。
2. `swift test --package-path LedgerKit`：全部核心测试，含演示安装，并生成报表输出 `samples/reports.json`。
3. `tools/fixtures/check_reports.py` 用 Beancount 对照 Swift 报表。输出中的 "N errors loading the sample" 属正常，以 "Reports match Beancount" 为准。
4. 删除并新建专用模拟器 "Ledger Local Tests"（优先 iPhone 17、16，运行时匹配 Xcode 的 SDK），关闭硬件键盘，等待 `bootstatus` 与 launchd 响应后才开始测试，不靠固定等待。
5. XcodeGen 生成工程，`build-for-testing` 编译 App（不含内置演示）与 LedgerTests、LedgerUITests。
6. `test-without-building` 运行全部附件与交互测试，不并行，单个测试时限 300 秒。

测试失败修业务或测试的真实原因，不删测试、不放宽断言、不靠重跑凑绿。模拟器在测试开始前就失败，属于环境问题，可以直接重跑。

日志留在仓库根目录：`swift-tests.log`、`reports-check.log`、`demo-build.log`、`interaction-tests.log`、`interaction-tests.xcresult`（用 Xcode 打开看失败截图），均不入库。

## dev：开发版

1. 前置检查：在 main 分支、工作区没有未提交的改动、本地 main 包含 GitHub main。
2. 运行上面的全部验证。
3. 构建号取所有已发布开发版与正式版中最大的构建号加 1；版本号取 `project.yml` 的 `MARKETING_VERSION`。
4. 把 `.demo-data` 复制进 `Ledger/Demo` 作为内置演示，Release 编译 iphoneos，ad-hoc 签名；校验签名、版本、构建号、内置演示与 ZIP 完整性。
5. 确认验证和编译期间源码没有变化，生成 `dist/` 下的 `Ledger.ipa`、`validation-evidence.json`（本机验证结果）、`build-manifest.json`（源码、文件树、版本、构建号、SHA256）、`release-notes.md`。
6. 普通推送 main（不强推），然后更新 `dev` 预发布 Release 与 `ipa` 分支上的 IPA 源。

发布说明从 CHANGELOG 当前版本读取，只列出与上一次开发版相比新增或修改的条目。

## release：正式版

Kerwin 在手机上按 [06 手机验收清单](06-手机验收清单.md) 验收开发版后执行。脚本下载当前 `dev` 的安装包与记录，核对 SHA256、版本、构建号、签名资源、本机验证记录，以及源码提交确实在 GitHub main 上且文件树一致，然后发布 `vX.Y.Z` 并更新正式版 IPA 源。不重新编译：正式版就是验收过的同一个安装包。

发布后把 CHANGELOG 中这一版的标题从「（开发中）」改为「（YYYY-MM-DD 发布）」（北京时间），单独提交并普通推送 main；脚本不会自动改。下一个版本开始前先执行 `ship.py version`。Kerwin 也可以明确授权代为执行 `release`。

已发布的版本不覆盖、不移动标签。正式版有问题就发新的补丁版本：`ship.py version patch` → 修复 → `ship.py dev` → 手机验收 → `ship.py release`。

## IPA 源

`ipa` 分支上有两个渠道、各两个地址（同名文件，GitHub 直连与经 gh-proxy.com 的镜像）：

| 渠道 | GitHub | 镜像 |
| --- | --- | --- |
| 开发版 | `https://raw.githubusercontent.com/<仓库>/ipa/dev.json` | `https://gh-proxy.com/https://raw.githubusercontent.com/<仓库>/ipa/mirror/dev.json` |
| 正式版 | `https://raw.githubusercontent.com/<仓库>/ipa/release.json` | `https://gh-proxy.com/https://raw.githubusercontent.com/<仓库>/ipa/mirror/release.json` |

在 SideStore、AltStore、Zeus 等支持 IPA 源的工具中添加任一地址。镜像版里源、图标和安装包都经 gh-proxy.com 下载，安装包地址带版本与构建号，避免镜像缓存旧包；gh-proxy.com 是第三方公共服务，不可用时改用 GitHub 地址。这是用自己的 Apple ID 重新签名的自签分发，不是 App Store 或 TestFlight。

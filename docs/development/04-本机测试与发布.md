# 04 云端测试与发布

## 1. 执行位置与规则

测试、模拟器、Release 编译、打包、开发版发布、正式版转正和 IPA 源更新全部在 GitHub Actions 的 macOS runner 执行。本机只编辑、做轻量静态/工具检查、提交、普通推送并发起云端任务，不启动 Xcode 编译或模拟器。继续直接在 main 提交，不设 PR 门禁。

入口仍是 `python3 tools/ship.py`：本机调用时转交 `tools/cloud.py`，GitHub 执行 `.github/workflows/ledger.yml` 和 `tools/cloud_worker.py`。工作流只手动触发，不因普通推送自动发布。源码要先推送到 main 才能由 GitHub 验证；云端失败时源码可能已推送，但不会继续发布安装包。

分别汇报：源码提交、指定/全量测试实际结果、安装包和发布状态、手机验收。编译成功不能代替测试通过，指定测试不能代替全量，未验收一律写“待手机验收”。

## 2. 一次性配置

- 仓库启用 Actions；使用 GitHub 托管 `macos-26`，不使用本机 runner。
- 本机安装 Python 3 和 `gh`，执行 `gh auth login`；登录需能推送仓库、修改 workflow、触发和查看 Actions。
- 工作流用内置 `GITHUB_TOKEN`，声明 `contents: write`，用于 Release、开发版标签和 IPA 源。不需要上传个人 Token 或 Apple 签名证书。
- runner 安装 XcodeGen、Python 3.12 和固定 Beancount 3.2.0，记录实际 Xcode 与模拟器版本。IPA 沿用临时签名、自签安装方式，用户仍在手机安装工具里用自己的 Apple ID 签名。
- 演示数据只读克隆 `iskerwin/ledger-demo`，固定到 manifest 的公开提交；永不读取私人账本。

## 3. 日常开发与指定回归

先提交改动并维护 CHANGELOG，再发起对应测试。命令会检查工作区干净、当前在 main、没有落后远端，然后普通推送并发送任务；返回任务链接不代表测试通过。

```sh
# 只跑指定核心测试，不编译 App，不发布
python3 tools/ship.py test --core-filter 'CalendarMarkTests|PostingOrderTests'

# 只跑一个必须看界面的回归；自动编译 App 和测试包
python3 tools/ship.py test --ui-test LedgerUITests/EditInteractionTests/testCalendarUsesFullRowWidthWithoutHint

# 同一任务可组合核心和多项界面/App 内回归
python3 tools/ship.py test --core-filter CalendarMarkTests \
  --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelection \
  --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelectionAtLargeText

# 指定窄屏机型；运行时不支持就报环境问题，不偷偷换宽屏
python3 tools/ship.py test --device 'iPhone SE (3rd generation)' \
  --ui-test LedgerUITests/EditInteractionTests/testGlassCalendarFixedRowsAndDaySelection
```

`--ui-test` 支持 `Target/Class` 或 `Target/Class/method`，可重复。`--core-filter` 沿用 `swift test --filter` 语法。指定测试必须实际执行、有通过数、没有失败或跳过，并核对请求的每个选择器都执行到了；空结果不能算通过。指定回归记录为 `scope=build`，包含实际筛选、通过数和设备，永不写成全量记录。

测试分层：LedgerKit 放解析/金额/格式/报表逻辑；LedgerTests 放必须在 App 内运行的存储、上传、恢复；LedgerUITests 放键盘、弹层、手势、跳转、布局。每个 bug 配修复前会失败的最低层回归。涉及共用组件、保存、同步、隔离或记账计算时扩大相关模块范围。切换布局检查常用字号、较大字号与窄屏。

本机只做轻量检查：

```sh
python3 tools/check_project.py
python3 -m unittest discover -s tools/tests -p 'test_*.py'
git diff --check
```

只改文档/工具时不用编译未变动的 App。必要的 App 构建检查可在云端发起相关界面回归，或通过开发版任务的 Release 构建完成。

## 4. 验证后打包并发布开发版

```sh
# 小修复：同一云端任务先跑相关回归，通过才编译 IPA、发布和更新源
python3 tools/ship.py dev --core-filter CalendarMarkTests \
  --ui-test LedgerUITests/EditInteractionTests/testCalendarUsesFullRowWidthWithoutHint

# 仅轻量改动，已另行确认相关测试：静态/工具检查、编译打包发布
python3 tools/ship.py dev

# 大范围改动：全量通过后打包发布
python3 tools/ship.py dev --full
```

顺序：静态检查与工具回归 → 指定回归或全量（如指定）→ 计算版本/递增构建号 → Release 编译并内置固定演示 → 校验签名资源、版本、ZIP、演示内容和 SHA256 → 核对源码没变化且仍是远端 main 最新提交 → 发布开发版 → 更新 IPA 源。任何前置步骤失败都停止后续；旧源码任务不会覆盖较新的开发版。所有开发版/转正任务共用云端发布锁，不自动取消正在发布的任务。

默认 `dev` 不跑全量，发布说明必须明确实际验证范围。已知测试失败要报告 Kerwin，由他决定下一步，不能用不带筛选的 `dev` 绕过已知失败。网络错误可能留下已更新的 Release 或部分附件；先查实际状态再重试，不删除 Release/标签/分支，不强推 main。

## 5. 完整测试

```sh
python3 tools/ship.py test
# 或明确写 --full，效果相同
python3 tools/ship.py test --full
```

只验证，不打包或发布；不能和指定筛选混用。云端串行执行：静态与工具回归 → LedgerKit 全部测试 → Beancount 报表对照 → 新建专用模拟器、关闭硬件键盘并确认启动 → 编译 App 和测试包 → 全部 LedgerTests 与 LedgerUITests。

以 `Reports match Beancount` 为报表一致结论；样本加载的预期提示不是失败。界面测试不并行，每项时限 300 秒。读取 `.xcresult` 汇总和用例明细，两个测试目标都要有非零通过数；失败、跳过、零项、漏目标或结果不可读均不算全量通过。验证记录绑定源码 SHA、文件树、演示提交与内容摘要，记录运行链接、Xcode、设备、核心与两个 App 测试目标通过数。

失败即停，未运行、失败、中断分别记录，不删测试、不放宽断言、不靠重跑凑绿、不用固定延时掩盖时序。测试尚未开始的模拟器环境失败可重跑。

## 6. 手机验收与正式版

Kerwin 安装开发版，按 [06](06-手机验收清单.md) 验收，明确记下构建号。只有验收后由 Kerwin 执行，或明确授权代为执行：

```sh
python3 tools/ship.py release --accepted-build 40  # 示例，填实际已验收构建号
```

本机只读取当前开发版清单，核对已验收构建号，再把构建号和 IPA SHA256 绑定到云端任务。云端重新下载开发版，核对 SHA256、大小、版本、构建号、签名资源、演示内容、源码在 main 上、标签与源码一致；任何验收身份变化都停止。网页手动发起 release 同样必须填已验收构建号与 SHA256。

完整全量证据存在时直接复用；独立 `test` 的全量记录另存 90 天的小型 artifact，转正自动查找同一源码和演示摘要的成功任务记录；缺少时用当前发布工具在独立工作区检出安装包对应源码，补跑全量验证，不能测试最新 main 代替。旧本机证据保持兼容，但缺演示摘要、检查记录或两个测试目标通过数时仍需补跑。全量失败/中断停止转正。

通过后把原 IPA 原样发布为正式版，不重新编译 IPA，并更新正式版源。正式标签/Release 一经发布不覆盖、不移动、不删除。发布后单独将 CHANGELOG 的“开发中”标题改为北京时间发布日期、提交并普通推送；下一版本仍用 `ship.py version` 开始。转正绝不自动触发，也不代表本轮开发任务已获转正授权。

## 7. 任务、日志和截图

```sh
python3 tools/ship.py watch --once  # 查看最近一次发起的云端任务
python3 tools/ship.py watch         # 等待并返回云端任务成功/失败状态
# 也可直接用任务链接，或 gh run view / gh run watch / gh run download
```

客户端只在 `.ship/cloud.json` 保存请求、源码和任务编号；不会在本机跑测试。客户端被关闭时云端继续执行。每轮都有独立任务链接；错误或中断时核查 main、Actions、Release 与安装源，不一律声称“未推送、未发布”。

工作流无论成功或失败，都上传 14 天 artifacts：阶段状态、核心/工具/编译/交互日志、`.xcresult`、导出截图、实际验证记录，以及已经产生的 IPA/清单/说明。日志中可能保留失败前的部分结果；只有任务结论和完整证据一致才算通过。Release 中的 IPA、清单、验证记录和发布说明长期保留，不依赖短期 artifacts。runner 超时或外部取消时可能来不及收集全部附件，不能写成通过。

## 8. 版本和安装源

版本号由 `python3 tools/ship.py version patch|minor|major|X.Y.Z` 在本机修改并提交；这是轻量源码操作。开发中同一版本继续积累 CHANGELOG，不因每次开发版重升版本号。构建号在云端取完整 Release/标签及 IPA 源历史最大值加一；列表不完整就停止。发布说明自动由 CHANGELOG 生成，并区分指定回归、全量及手机验收状态。

IPA 源保留在 `ipa` 分支：`dev.json`、`release.json`、`mirror/dev.json`、`mirror/release.json`；地址和自签安装方式不变，镜像仍由第三方 gh-proxy.com 提供。安装工具用用户自己的 Apple ID 重新签名。

## 9. 云端环境依据

runner 标签与预装软件以 GitHub 官方 [runner 说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job) 和 [macOS 26 镜像清单](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md) 为准。固定 runner 标签，实际 Xcode/运行时随镜像更新，记录到每次任务；不把某轮设备结果泛称为所有系统版本已验收。

# 07 开发计划

这是待选清单，不是承诺：每条由 Kerwin 选定后，再按 [AGENTS.md](../../AGENTS.md) 说明前后变化、确认范围，一件事一个分支。做完的条目从这里删掉，结果记在 CHANGELOG，不在这里记发布状态。

每条写明：现在什么样、做了以后看到什么、为什么值得做、工作量（小 / 中 / 大）、风险、建议（做 / 暂缓 / 不做）、依赖和验收方式。组内按性价比从高到低排。没量过的性能问题一律写「先测量」。

本清单（2026-11-16）的依据：01 功能清单、手机「使用指南」的每一条，逐项对照 `LedgerMac/` 的页面、按钮和右键菜单；还有云端运行记录和关闭的 PR。界面实际观感（间距、对齐、动效）这次没有逐屏走查，见第 21 条。

## 一、Mac 与手机的功能对齐

Mac 已有：
- **页面**：概览、明细（表格、排序、多选、修改原文；右键复制为新交易、登记退款、调整当天顺序）、账户（管理账户、核对余额）、报表、收付款方、年度回顾、预算（管理预算）、现金流预测、订阅（添加、调价、暂停、取消、跳过、修正、删除、记一笔扣费）、报销（登记回款、导出报销单、垫付的支出类型与凭证、移出）、工资、事件、值得留意、BQL 查询（保存、导出 CSV）、附件与对账单、同步与改动。
- **记账**：记一笔窗口（快捷卡片和完整表单，含退款、AA、报销、组合付款）。
- **其他**：多步撤销和重做、中英文、菜单栏「交易」（所选交易的右键操作）和「帮助 › Ledger X 使用指南」、「文件 › 打开最近使用」。

### 3. Mac 订阅和报销剩下的手机操作

- **现在**：订阅的关联已有交易、撤销历史里的某一条、整理订阅记录，报销的备用金冲抵、退回备用金、把垫付加入已有报销单、导出已结清的报销单，仍只能在手机上做。
- **做了以后**：Mac 上订阅和报销页与手机完全一致。
- **为什么**：这些都不常用，写入规则已在 LedgerKit（`SubscriptionEdit.swift`、`ReimbursementEdit.swift`），补起来主要是界面。
- 工作量：小到中。风险：低。
- **建议：等 Kerwin 用到时再做。** 验收：Mac。

### 4. Mac 批量编辑

- **现在**：Mac 明细表格能多选，但只能批量复制原文；批量改分类、账户、标签只能在手机上做。
- **做了以后**：在表格里选中多笔，右键批量修改。
- **为什么**：大屏多选最适合批量整理。
- 工作量：中。风险：中，一次改多笔，靠提交前检查和撤销兜底。
- **建议：做。** 验收：Mac。

### 6. Mac 往来页

- **现在**：手机「账户 → 往来」按人汇总借出、代付、AA 和还款。Mac 侧栏的「往来」分组里只有报销、工资、事件，看不到按人汇总，也不能登记别人还钱。
- **做了以后**：Mac 有往来页，显示每个人的余额和明细，可以登记还款。
- 工作量：中。风险：低（`Counterparty.swift` 已共用）。
- **建议：做**，排在 1–4 之后。验收：Mac。

### 7. Mac 快速搜索

- **现在**：手机明细搜索后可以「保存」成快速搜索，一点即用，存在账本的 `ledger-x.json` 里。Mac 有同样的搜索语法，但看不到也不能保存这些快速搜索。
- **做了以后**：Mac 搜索栏旁列出同一批快速搜索，可点用、保存、编辑，两端自动一致。
- 工作量：小。风险：低（数据已在共享配置里）。
- **建议：做。** 验收：Mac。

### 8. Mac 账单导入（CSV / XLSX）

- **现在**：只有手机能导入银行或支付平台账单。
- **做了以后**：在 Mac 上选文件、对应列、核对查重、确认入账，大屏核对几十上百行更轻松。
- **为什么**：解析、查重和导入恢复都在 LedgerKit（`Import.swift`、`Xlsx.swift`、`ImportRecovery.swift`），Mac 只需要界面和本机进度。
- 工作量：大。风险：中，导入进度要按账本隔离。
- **建议：做，排在前面几条之后。** 验收：Mac。

### 9. Mac 投资持仓、更新价格和币种看法

- **现在**：
  - Mac 没有持仓页，也不能联网更新证券和外币价格。
  - Mac 各页一律折算成主币种显示。手机导航栏的币种面板能选原币、按成本、按市值或折算，Mac 没有。
- **做了以后**：Mac 账户里能看持仓和盈亏，一键更新价格；报表和账户页可以切换币种看法。
- **为什么**：有投资或外币账户时，净资产要靠最新价格才准确；对账要看原币。
- 工作量：中到大。风险：低。依赖第 19 条（取价代码移进 LedgerKit）。
- **建议：做**，没有投资和外币账户就暂缓。验收：Mac。

### 10. 分类图标、排序和常用交易两端共享

- **现在**：分类的图标、名称、顺序和大类的颜色只存在手机本机、不进账本。Mac 看不到这些，宫格也不能改；常用交易不能置顶，账户不显示卡号尾号（03 里写着「不做」）。
- **做了以后**：两端分类长得一样、顺序一样。
- **为什么**：两端看起来一致，就少一层困惑。
- 工作量：中。风险：中。要共享就得写进 `ledger-x.json`，这是数据契约的变化，还要处理两台设备同时改的情况。
- **建议：你先决定要不要共享。** 不共享的话，Mac 自己存一份也可以，工作量小。

### 有意不同（建议不对齐）

| 手机有、Mac 没有 | 理由 |
| --- | --- |
| GitHub / GitLab / Gitea / WebDAV 连接、离线队列、同步与最近改动 | Mac 直接打开本机文件夹，用本机 git 同步，并有多步撤销（见 03） |
| 面容 ID 锁、钥匙串里的卡片信息、提醒、快捷指令与 Siri | 手机平台功能 |
| 卡面账户卡片、明细三种行样式、金额圆体、主题色选择 | 都是显示样式，Mac 用表格和固定的翡翠色，暂时不需要；想要两端同色可以单独提 |
| 演示账本、新建空账本、多账本列表 | Mac 用「打开账本…」选文件夹，「打开最近使用」切换最近几本 |
| 统计范围设置、排版规则、iCloud 备份与 zip 导出 | 在手机设置一次即可（统计范围和排版写在 `ledger-x.json`，Mac 照样读）；Mac 上账本本来就在本机 |

Mac 独有的多步撤销重做、表格排序多选、git 差异页，手机已有对应做法（最近改动撤回、筛选、改动核对），不需要搬回手机。

## 三、底层代码与架构

### 16. 先在真机量保存后的重建时间

- **现在**：手机每保存一笔都会重新解析整本账本。云端用 6 万笔样本测过，门槛已收紧，但不知道你实际的账本在真机上要多久。
- **做法**：在你的手机上看 `SaveTiming` 的数字。不读私人账本内容，只看耗时。
- **决定**：超过约 0.3 秒，才值得做「只重新解析改动的文件」。那是大工程：余额、持仓这类跨文件结果仍要全量重算。
- **建议：先测量，再决定。**

### 18. 给 Mac 加最少量的界面测试

- **现在**：Mac 只有 LedgerKit 的逻辑测试和编译检查。打开账本、记一笔、撤销、换语言这些流程全靠人工验收。
- **做了以后**：云端自动跑几条 Mac 冒烟测试（打开虚构账本 → 记一笔 → 撤销 → 切英文），改坏了合并前就能发现。
- 工作量：中。风险：低，云端多几分钟。
- **建议：做。**

### 19. 把取价等平台无关代码移进 LedgerKit

- **现在**：联网取价（`Ledger/Sync/PriceFetch.swift`）放在手机端，Mac 用不了。
- **做了以后**：用户看不到变化；第 8、9 条可以直接复用，两端算法一致。
- 工作量：小到中。风险：低（只搬家，配测试）。
- **建议：做第 8、9 条时一起做**，不单独做。

### 已核对、不需要改

- **两端写账路径**：手机和 Mac 都经过 LedgerKit 的 `makeOps` / `applyOps` 和同一套提交前检查。分叉只在之后：手机进队列再推送，Mac 直接写文件。这是有意的设计，没有重复的账务逻辑。

### 不建议现在做

- **拆大文件**：`Store.swift`、`QuickAddView.swift` 等单文件 1100–1700 行。没有实际问题时成批拆，违反「只做实际需要的改动」；改到哪个再顺手整理。
- **两端共用界面代码**：03 已决定 Mac 和手机界面分开写。共用 SwiftUI 代码会让两边互相牵制。

## 四、测试与发布流程

### 20. 交互测试变慢、变脆

- **现在**：
  - 转正前全量里的「附件与交互测试」标着约 20 分钟，实际是常态性的慢：1.0.13 约 64 分钟、1.0.14 约 66 分钟、1.0.15 约 50 分钟、构建 67 约 79 分钟（失败）、构建 68 约 74 分钟。
  - 月历滚轮测试两天里因时序修了 4 次。
  - 慢机器上读一次界面元素要约 4 秒。
- **做了以后**：每次全量报告最慢的 10 个界面测试及耗时；能用 LedgerKit 测的逻辑从界面测试挪下去，界面测试只留必须看界面的部分。转正更快，也不再被偶发超时卡住。
- 工作量：中。风险：低。
- **进度**：耗时报告已加上，每次全量的日志和 Actions Summary 都列出最慢的 10 个界面测试。
- **已修**：2026-11-15 每周全量 193 个界面用例共 71 分钟，最慢的 126 秒。云端每查一次界面约 1 秒，而 19 处「滚动或等待直到出现」的循环写成 `for … where`，找到后仍把剩下的次数查完（每处多花数秒到数十秒）。已改为找到就停，`check_project.py` 禁止再这样写。
- **偶发超时**：2026-11-16 PR #189 的「import duplicates」在同一份代码上从 0.04 秒跳到 0.91 秒，重跑 0.05 秒通过；再出现就查测量方法或云端机器，不只重跑。
- **建议：做。** 下一步看改后第一次全量的报告，再逐个处理仍然最慢的几个。

### 21. 界面观感走查

- **现在**：这份清单没有逐屏看实际界面（间距、对齐、换语言后的换行、深色模式、大字号）。
- **做法**：用虚构账本在模拟器和 Mac 上截一套中英文、深浅色、常用和大字号的截图，逐页列出不一致，再挑要改的。
- 工作量：中。风险：无（只看不改）。
- **建议：做**，结果补进本清单。

### 22. 失败运行的证据自动清理

- **现在**：失败运行的日志、截图、录屏在云端留 7–30 天，问题修好后就没用了。11 月 16 日手动清掉了 48 份，约 3 GB。
- **做了以后**：正式版发布成功后，自动删掉这一版已经取代的失败证据；运行记录和 PR 测试记录照常保留。
- 工作量：小。风险：低，删前核对没有还开着的 PR。
- **建议：可选。**
